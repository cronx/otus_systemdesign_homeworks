## 0. Контекст системы

- Система предоставляет пользователям возможности загрузки и просмотра видео разных размеров

**Основные акторы:**
- конечный пользователь - просматривает видео, ставит лайки, комментарии
- автор контента - создает канал, загружает видео, просматривает аналитику, просматривает комментарии, реакции
- модератор - просматривает видео

**Ключевые сценарии использования:**
- кодирует и загружает видео к себе в хранилище
- предоставляет видео по запросу
- предоставляет связанные с видео артефакты (реакции, комментарии)

**Масштаб:**
- пользователей всего - 1 миллиард
- пользователей онлайн - 50 млн
- файлов всего - 20 миллиардов файлов всего
- ежедневный прирост новых видео - 20 миллионов файлов = 900 Тб в сутки
- одновременное скачивание видео в пике - 450 Тб/с
- одновременные запросы - 5 млн rps


## 1. Компоненты

_Основные сервисы и их ответственности (5–10 компонентов)._

| Компонент | Ответственность |
|---|---|
| WebClient | (Мобильный и веб клиенты) Пользовательский интерфейс |
| API | **Load Balancer / API Gateway** (сервис, балансировщик) - обрабатывает входящие запросы |
| AuthService | (сервис) - проверяет, какие пользователь имеет права (и имеет ли) |
| Upload Service | (сервис) Управляет загрузкой видео в храилище|
| Object Storage | (файловое хранилище, s3) - хранит исходные загруженные файлы |
| DB | (бд) Хранит метаданные видео |
| Broker | (очередь) - управляет очередью заданий, в тч на преобразование загруженных видео, асинхронно |
| TranscodingService | (сервис) - преобразовывает исходные видео в нужную кодировку, разбивает на чанки |
| Publication Service | (сервис) управляет публикацией видео|
| VideoService | (сервис) управляет метаданными и статусами видео|
| CommentService | (сервис) управляет публикацией комментариев|
| CDN | (хранилище, кеш) хранит чанки видео для загрузки пользователями |

## 2. Потоки данных

### Сценарий 1: Пользователь загужает видео
**Порядок взаимодействия**
1. **Пользователь** — в WebClient выбирает видеофайл и инициирует загрузку
2. **WebClient** — отправляет в API запрос на загрузку видео
3. **API** — обращается к AuthService для проверки прав пользователя, синхр
4. **AuthService** — проверяет права пользователя и возвращает результат в API. Если нет прав то пользователю отображается ошибка.
5. **API** — перенаправляет запрос на создание загрузки в Upload Service, асинхр
6. **Upload Service** — сохраняет метаданные видео в DB
7. **WebClient** — передаёт видеофайл в Object Storage
8. **Object Storage** — сохраняет видеофайл. При сбое - retry
9. **WebClient** — уведомляет Upload Service через API о завершении загрузки
10. **Upload Service** — проверяет наличие загруженного файла в Object Storage
11. **Upload Service** — отправляет в Broker событие что загружен файл и нужно его обработать
12. **Broker** — передаёт событие в TranscodingService
14. **TranscodingService** — получает видеофайл из Object Storage, перекодирует видео в несколько разрешений и форматов, сохраняет обработанные версии видео в Object Storage.
15. **TranscodingService** — уведомляет Publication Service о завершении обработки видео
16. **Publication Service** — обновляет статус видео в DB на READY, синхр
17. **CDN** — при первом запросе получает необходимые видеосегменты из Object Storage и кэширует их для последующих просмотров. Затем держит в кеше

### Сценарий 2: Пользователь в клиентском приложении открывает ссылку на просмотр видео

1. **Пользователь** — открывает ссылку на видео в WebClient.
2. **WebClient** — отправляет запрос в API на получение информации о видео
3. **API** — обращается к AuthService для проверки пользователя
4. **AuthService** — возвращает в API сведения о пользователе и его правах доступа
5. **API** — отправляет запрос в VideoService
6. **VideoService** — запрашивает в DB метаданные видео
7. **DB** — возвращает метаданные видео 
8. **VideoService** — проверяет доступность видео для пользователя и формирует параметры воспроизведения
9. **VideoService** — возвращает информацию о видео в API
10. **API** — передаёт информацию о видео в WebClient
11. **WebClient** — запрашивает у CDN данные о наличии нужных видео (чанков)
12. **CDN** — проверяет наличие видео (чанков) в кэше и при отсутствии получает их из Object Storage
13. **CDN** — передаёт чанки в WebClient
14. **WebClient** — начинает воспроизведение видео пользователю

### Сценарий 3: Пользователь оставляет комментарий к видео

1. **Пользователь** — вводит текст комментария под видео и нажимает кнопку отправки
2. **WebClient** — отправляет в API запрос на создание комментария
3. **API** — обращается к AuthService для проверки аутентификации пользователя
4. **AuthService** — проверяет пользователя и возвращает результат проверки
5. **API** — передаёт запрос на создание комментария в CommentService
6. **CommentService** — обращается к VideoService для проверки существования видео и возможности его комментирования
7. **VideoService** — запрашивает в DB сведения о видео и настройках комментирования

9. **VideoService** — проверяет доступность комментирования
10. **CommentService** — проверяет корректность комментария, создаёт идентификатор комментария и сохраняет его в DB с привязкой к видео, возвращает результат создания комментария

17. **NotificationService** — определяет автора видео и формирует уведомление о новом комментарии

## 3. Проблемы и решения

| Компонент | Какие проблемы решает |
|---|---|
| WebClient | дает пользователю возможность взаимодействовать системой |
| API | распределяет входящие запросы между сервисами |
| AuthService | отвечает чтобы доступ к видео не был получен несанкционированно |
| Upload Service | забирает на себя нагрузку по обработке части запросов |
| Object Storage | самое большое хранилище данных, от него нужно сохранить исходные файлы, для этого снижаем нагрузку входящими запросами, и для пользователей видео предоставляем через CDN |
| DB | обеспечивает хранение метаданных, чтобы иметь актуальную информацию в каком статусе видео, кто автор, как называется и т.д. |
| Broker | позволяет выстроить надежную асинхронную обработку внутренних тяжелых запросов |
| TranscodingService | забирает на себя функции преобразования видео |
| Publication Service | просто забирает на себя часть функций связанных с публикацией видео, чтобы диверсифицировать нагрузку |
| VideoService | просто забирает на себя часть функций , чтобы диверсифицировать нагрузку |
| CommentService |просто забирает на себя часть функций связанных с публикацеий комментариев , чтобы диверсифицировать нагрузку|
| CDN | обеспечивает быстрый доступ пользователей к видео, для скорщаения времени ожидания и нагрузки на промежуточные сервисы, чанки видео передаются от CDN непосредственно в WebClient, минуя прикладные сервисы API и VideoService, держит чанки видео в геораспределенных хранилищах , отдаёт чанки клиентам из кэша без обращения в Object Storage  |

## 4. Вопросы к авторам архитектуры

1. Зачем отдельно выделять сервис публикации видео отдельно от upload сервиса?
2. В текущей архитектуре брокер в основном используется для упарвления запросами загрузки видео. Между API м отдельными внутренними сервисами как будто тоже нужно обеспечить очередь запросов. Правда там синхронное взаимодействие. Но почему там нет тоже обработки запросов через очередь?
3. Объемы данных в Object Storage огромные. Как обеспечивается его постоянная доступность?
4. Поскольку WebClient забирает видео чанки напрямую из CDN, то как обеспечивается безопасность этого обмена? Ведь получается любой WebClient в обход AuthService может получить видео?
5. Из описания ObjectStorage хранит только исходные файлы, до их перекодирования и разбивки на чанки. А CDN работает как кэш. Значит CDN должен откуда то получать эти самые готвоые перекодированные чанки, откуда он их берет? Как будто не хватает постоянного хранилища готовых чанков.
